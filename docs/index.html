THE EVIDENCE DESK / 01

Follow the receipt.

Interactive guide · not a live test

A result is only useful if you can see how it was reached—and where it stops.

01Compare

The same test runs against the base and head revisions. The comparison informs an advisory verdict.

02Inspect

A signed receipt records the result and can be verified offline. See an actual receipt ↗

03Know the limits

A valid signature is not proof that the code is correct. The verdict may be inconclusive. Read the report ↗

jittest doesn't read your diff and guess. It runs the same test on the base revision and the head revision in separate environments, then issues one of six verdicts — from proven_catch to a loud inconclusive — as an Ed25519-signed receipt anyone can re-verify offline.

In a published snapshot of 83 historical pull requests, 24 received definitive verdicts and 59 were inconclusive. The report notes a dirty snapshot and no sandbox; this is not a general success rate.

[ 05 ] Process

How a
claim earns
its place.

The working loop: state the claim, build the harness, try to break it, and leave a way for someone else to inspect the result.

01

State the claim

Write down exactly what will be true — and what won't. The boundary is part of the spec, not a disclaimer added later.

02

Build the harness

Tests, fixtures, frozen cohorts, pinned images. If it can't be measured, it doesn't ship as a claim.

03

Try to break it

Premortems, stress and chaos runs, adversarial payloads, tampered receipts. The tool gets turned on its own history.

04

Ship the receipt

A source, a reproducible command or a reviewable artifact—with signing where supported, and an explicit limitation when the evidence is not there.
